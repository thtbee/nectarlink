# Nectarlink Protocol — version 0 (draft)

> Status: **draft for Phase 0.** Breaking changes are allowed until v1.
> License: CC BY 4.0. Anyone may implement this protocol.

This document specifies how two Nectarlink devices find each other, pair,
connect and exchange messages. Version 0 covers the Phase 0 scope: identity,
pairing, the session handshake, capabilities, heartbeat and the first events
(device info, battery, ping). Feature services (notifications, files,
clipboard, mirroring…) are specified in separate documents that build on this
one.

Key words **MUST**, **SHOULD** and **MAY** are used as in RFC 2119.

---

## 1. Concepts

| Term | Meaning |
|---|---|
| **Device** | One installation of Nectarlink (a phone, a PC). |
| **Device key** | An Ed25519 key pair generated on first launch. Never leaves the device. |
| **Device ID** | The Ed25519 public key (32 bytes). Equal to the iroh `EndpointId`. Displayed as lowercase z-base-32. |
| **Pairing** | A one-time ceremony after which each device stores the other's Device ID as trusted. |
| **Session** | One authenticated QUIC connection between two paired devices. |
| **Service** | A feature area (e.g. `notifications`, `transfer`) that owns its own streams and messages. |

## 2. Transport

- All traffic runs over **QUIC via iroh**. TLS 1.3 with raw public keys
  authenticates both ends by Device ID. There is no other encryption layer and
  no unencrypted mode.
- Two **ALPN** values are defined:

  | ALPN | Purpose | Who may connect |
  |---|---|---|
  | `nectarlink/0` | Normal sessions | Paired devices only |
  | `nectarlink-pair/0` | Pairing ceremony | Anyone, but only while the receiving device is in pairing mode |

- A device **MUST** close a `nectarlink/0` connection immediately (application
  error `UNPAIRED`, see §8) if the peer's Device ID is not in its trust store.
- A device **MUST** reject `nectarlink-pair/0` connections when it is not in
  pairing mode, and **MUST** leave pairing mode after a successful pairing or a
  timeout (default 5 minutes).

### 2.1 Address discovery

Devices locate each other by Device ID. Implementations use, in order of
preference (iroh races them):

1. Local-network discovery (mDNS address lookup).
2. Last known direct addresses, cached per paired device.
3. A small UDP beacon on the LAN as a fallback where mDNS is filtered
   (format to be specified in v0.1).
4. Relay servers, only if the user enabled "away from home".

## 3. Framing

Every QUIC stream carries a sequence of **frames**:

```
frame = length (unsigned LEB128, 1–4 bytes) || payload (CBOR, `length` bytes)
```

- `length` **MUST NOT** exceed 1 MiB (1,048,576) for control and RPC streams.
  Receivers close the stream with `FRAME_TOO_LARGE` otherwise.
- Bulk data (file contents, video) does **not** use frames. After its header
  frame, a bulk stream switches to raw bytes as defined by its service.
- All CBOR payloads are maps. Unknown keys **MUST** be ignored.

### 3.1 Message envelope

Every frame payload is an envelope:

| Key | Type | Required | Meaning |
|---|---|---|---|
| `t` | text | yes | Message type, e.g. `hello`, `event.battery` |
| `id` | uint | no | Request ID, unique per stream direction, for messages expecting a reply |
| `re` | uint | no | The `id` this message replies to |
| `b` | map | no | Message body (type-specific) |

A receiver that gets an unknown `t` carrying an `id` **MUST** reply with
`error` code `UNSUPPORTED`. Unknown `t` without an `id` is silently ignored.

## 4. Streams

| Stream | Opened by | Kind | Lifetime |
|---|---|---|---|
| **Control** | The dialing device | Bidirectional | The whole session. Must be the first stream opened |
| **RPC / service** | Either device | Bidirectional | One operation (a request and its response, or a service sub-session) |
| **Bulk** | Either device | Uni- or bidirectional | One transfer or media session |
| **Datagrams** | Either device | QUIC datagrams | Loss-tolerant, latency-critical data (pointer motion, input) |

Every non-control stream starts with a **stream header** frame:

```
t = "stream"
b = { svc: text, op: text, v: uint }
```

`svc` names the service, `op` the operation, `v` the operation's version. If
the receiver doesn't support it, it replies `error UNSUPPORTED` and closes the
stream.

Datagrams start with a one-byte channel tag (assigned per service in the
service specs), followed by service-defined bytes.

## 5. Session handshake

After the QUIC handshake, the dialer opens the control stream and sends
`hello`. The listener replies with its own `hello`. The session is
**established** once both `hello`s are exchanged and the version check passes.

```
t = "hello"
b = {
  proto:   uint,        // protocol version spoken (0 for this document)
  min:     uint,        // oldest protocol version this device still accepts
  app:     text,        // app version, e.g. "0.1.0"
  device:  DeviceInfo,
  caps:    [text],      // capability IDs this device offers (see §6)
  power:   text,        // "basic" | "assist" | "elevated" | "root" | "n/a" (desktop)
}

DeviceInfo = {
  name:     text,       // user-visible name, e.g. "Pixel 9"
  kind:     text,       // "phone" | "tablet" | "desktop" | "laptop"
  os:       text,       // "android" | "windows" | "macos"
  os_ver:   text,       // "16" / "10.0.26200"
  model:    text?,      // e.g. "Google Pixel 9"
  accent:   uint?,      // optional ARGB seed color (Material You sync)
}
```

**Version negotiation:** the session uses `min(proto_a, proto_b)`. If that is
below either side's `min`, the side that detects it sends `error
VERSION_TOO_OLD` and closes the connection, and both UIs tell the user which
side needs an update.

Either device may send an updated `hello.update` on the control stream at any
time (for example when the power level or capabilities change):

```
t = "hello.update"
b = { caps: [text]?, power: text?, device: DeviceInfo? }
```

## 6. Capabilities

A capability ID is a dotted string naming something a device *can offer*,
for example:

| Capability | Offered by | Meaning |
|---|---|---|
| `core.ping` | both | Responds to ping |
| `device.battery` | both | Sends battery events |
| `notify.mirror` | phone | Can forward notifications |
| `notify.sensitive` | phone | Can forward sensitive (OTP) notifications |
| `clip.read.auto` | phone | Can read the clipboard in the background |
| `mirror.elevated` | phone | Prompt-free mirroring with full control |

Capabilities describe **what the device can do right now** given its power
level, OS version, permissions and add-ons. Each app combines both devices'
capabilities with its own local state to compute the **capability matrix**
that drives the UI (see `docs/architecture/capabilities.md`). The full
registry of capability IDs lives in `docs/protocol/capabilities.md` and grows
with each service.

## 7. Messages in v0

### 7.1 Heartbeat

QUIC keep-alives keep NAT bindings open. In addition, either side **MAY** send
on the control stream:

```
t = "ping"   id = n   b = { ts: uint }        // sender's monotonic ms
t = "pong"   re = n   b = { ts: uint }        // echoes ts
```

A session with no traffic for 45 s **SHOULD** send a `ping`. Implementations
measure round-trip time from `ping`/`pong` for the connection-health indicator.

### 7.2 Events

Events are one-way notifications on the control stream. Their type starts
with `event.`.

```
t = "event.battery"
b = { level: uint (0–100), charging: bool, plugged: text? ("ac"|"usb"|"wireless") }

t = "event.device"
b = DeviceInfo                      // name or accent changed
```

### 7.3 Find my device

```
t = "device.ring"   id = n   b = { on: bool }     // start or stop ringing
t = "ok"            re = n
```

### 7.4 Errors

```
t = "error"   re = n?   b = { code: text, msg: text? }
```

## 8. Error codes

| Code | Meaning |
|---|---|
| `UNSUPPORTED` | Unknown message type, service or operation version |
| `UNPAIRED` | Peer is not in the trust store (also used as the QUIC close reason) |
| `VERSION_TOO_OLD` | Protocol version below the receiver's minimum |
| `FRAME_TOO_LARGE` | Frame exceeds the size limit |
| `BAD_MESSAGE` | Malformed CBOR or missing required fields |
| `DENIED` | The user or a per-device permission denied the operation |
| `BUSY` | Temporarily unable; retry later |
| `INTERNAL` | Unexpected failure on the receiver |

## 9. Pairing (`nectarlink-pair/0`)

Pairing establishes mutual trust between two Device IDs. Two flows are
defined. Both run over a `nectarlink-pair/0` QUIC connection, so the TLS layer
already authenticates the raw public keys; the ceremony proves that the
**human** intended *this* peer.

### 9.1 QR flow (primary)

1. The PC enters pairing mode, generates a random 128-bit **pairing secret**
   `S`, and shows a QR code containing a pairing URI:

   ```
   nectarlink://pair?v=0&id=<pc device id, z-base-32>&s=<S, base64url>&n=<pc name, percent-encoded>[&a=<ip:port>,...]
   ```

2. The phone scans it and dials the PC's Device ID with ALPN
   `nectarlink-pair/0`.
3. The phone sends:

   ```
   t = "pair.request"   id = 1
   b = { device: DeviceInfo,
         proof: bytes }   // HMAC-SHA256(S, "nectarlink-pair-v0" || phone_id || pc_id)
   ```

4. The PC verifies `proof` against the phone's TLS-authenticated Device ID. On
   success it stores the phone as trusted and replies:

   ```
   t = "pair.accept"    re = 1   b = { device: DeviceInfo }
   ```

   On failure it replies `error DENIED` and leaves pairing mode after 5 failed
   attempts.
5. The phone stores the PC as trusted. Both devices close the pairing
   connection and open a normal `nectarlink/0` session.

Because the phone learned the PC's Device ID from the QR code and the PC
verifies knowledge of `S`, both directions are authenticated with no codes to
compare.

### 9.2 Nearby flow (numeric comparison)

Used when the user picks a discovered device instead of scanning. The
initiator is **A**, the responder **B**.

1. A → B: `pair.commit { device, c }` where `c = SHA-256(nA)` and `nA` is a
   random 16-byte nonce.
2. B → A: `pair.nonce { device, nB }` with a random 16-byte nonce `nB`.
3. A → B: `pair.reveal { nA }`. B checks `SHA-256(nA) == c`.
4. Both compute the **short authentication string**:

   ```
   sas = uint32(HMAC-SHA256(nA || nB, "nectarlink-sas-v0" || idA || idB)[0..4]) mod 1,000,000
   ```

   shown as a 6-digit code on both screens.
5. The user confirms the codes match on **both** devices. Each sends
   `pair.confirm`. Only after receiving the peer's `pair.confirm` and
   confirming locally does each device store the other as trusted.

The commitment in step 1 prevents an attacker from choosing a nonce to force a
matching code; a man-in-the-middle would have different Device IDs on each
side and therefore different codes.

### 9.3 USB flow

When an ADB connection exists, the PC can exchange Device IDs with the phone
app over ADB directly. Specified in v0.1 together with the ADB integration.

### 9.4 Unpairing

Either device may send `pair.revoke` on an established session, then deletes
the trust entry. A device receiving it deletes its entry too. Unpairing
locally without notifying the peer is always allowed; the peer will then be
rejected with `UNPAIRED` on its next connection attempt.

## 10. Compatibility rules

1. Adding a message type, a field, a capability or a service is **not** a
   breaking change.
2. Removing or changing the meaning of a field, message or operation **is**
   breaking: it requires a new operation version (`v`) or a new protocol
   version.
3. Every app version **MUST** keep accepting the previous two protocol
   versions once v1 ships.
4. CI runs the current build against the previous two releases in both
   directions.

## 11. Security notes

- Device keys are stored encrypted at rest (DPAPI on Windows, Android Keystore
  wrapping on Android).
- The pairing secret is single-use, kept only in memory, and expires with
  pairing mode.
- Implementations **MUST NOT** log message bodies of notification, message,
  clipboard or file-name content.
- Frame and message decoders are fuzzed in CI.
